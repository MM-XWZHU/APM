## 三、用户界面与核心功能

| **智能基线告警** | 基于历史行为自动学习正常模式，异常波动自动告警 |

```
┌──────────────────────┐
│   用户体验监控 (RUM) │ ← Bonree ONE
├──────────────────────┤
│   应用性能监控 (APM) │ ← Bonree ONE（核心）
```

> - 当 Bonree ONE 发现“支付接口变慢”，可联动 InManage 查看底层服务器是否 CPU 打满或硬盘故障。
> - 反之，InManage 预警“某服务器硬盘将坏”，Bonree ONE 可评估该服务器承载的业务影响范围。

- 采用 **微服务、云原生、Serverless** 架构

### 🔧 最佳实践组合：
- **互联网公司**：Bonree ONE + Kubernetes 监控 + InManage（混合云场景）
- **银行核心系统**：Bonree ONE（手机银行/网银） + InManage（信创服务器） + DCIM（机房）

# 附3：既然很多硬件设备（如防火墙、交换机、服务器）已经自带监控或管理软件，为什么企业还需要像 Bonree ONE 这样的统一可观测性平台？
---

答案的核心在于：**“碎片化监控” vs “全局可观测性”**。

---

### 🔍 一、硬件自带监控的局限性

以防火墙为例，其配套软件通常具备以下能力：
- 查看设备 CPU/内存/吞吐量
- 监控安全策略命中情况
- 日志记录和基础告警

✅ **优点**：对本设备深度适配，功能精准。  
❌ **缺点**：**视角单一、数据孤岛、无法关联业务影响**

#### 具体问题包括：

| 问题 | 说明 |
|------|------|
| **1. 只看“自己”，不看“全局”** | 防火墙不知道应用是否卡顿、用户是否打不开页面。它只知道自己“正常”，但业务可能已中断。 |
| **2. 数据无法与其他系统打通** | 防火墙日志、数据库慢查询、K8s Pod 异常、前端 JS 报错——这些数据分散在不同系统中，无法自动关联分析。 |
| **3. 缺乏业务视角** | 硬件监控关注“设备是否活着”，而企业更关心“用户能否下单”“支付是否成功”。 |
| **4. 告警割裂，运维效率低** | 网络团队收到防火墙告警，应用团队收到服务超时告警，双方互相排查，耗时耗力。 |

> 🌰 举个例子：  
> 用户无法登录系统。  
> - 防火墙显示“一切正常”  
> - 应用日志显示“认证服务超时”  
> - 数据库显示“连接池耗尽”  
> - K8s 显示“Pod 频繁重启”  
> 如果没有统一平台，可能需要 4 个团队各自排查数小时。  
> 而 Bonree ONE 可通过**全链路追踪 + 拓扑发现 + 智能关联**，5 分钟内定位到根因是某个配置变更导致数据库连接泄漏。

---

### ✅ 二、Bonree ONE 的核心价值：**跨域融合 + 业务可观测**

Bonree ONE 不是要替代防火墙的管理软件，而是**在其之上构建一个更高维度的“数字神经中枢”**：

| 能力 | 说明 |
|------|------|
| **1. 多源数据融合** | 接入防火墙、交换机、服务器、云平台、APM、日志、业务埋点等，统一存储与分析。 |
| **2. 自动拓扑发现** | 自动绘制 IT 架构图，展示“用户 → 前端 → API → 微服务 → 数据库 → 网络设备”的完整依赖关系。 |
| **3. 全链路追踪** | 从用户点击到后端数据库，端到端追踪一次请求的完整路径和耗时。 |
| **4. 业务指标联动** | 将技术指标（如 API 延迟）与业务指标（如订单转化率）关联，回答“技术问题对生意的影响有多大？” |
| **5. AIOps 智能告警收敛** | 避免“一个故障触发上百条告警”，自动聚合并推荐根因。 |

---

### 🎯 三、类比理解

可以把 IT 系统想象成一座城市：

- **防火墙/交换机自带软件** = 各个路口的摄像头（只看到局部车流）
- **Bonree ONE** = 城市交通大脑（整合所有摄像头、GPS、信号灯、事故上报，实时优化全城交通）

你当然需要路口摄像头，但要治理拥堵、预测事故、保障救护车通行，必须靠“交通大脑”。

## 一、核心功能特性详解

### 1. **免配置集成化智能探针**
- **含义**：用户无需手动编写复杂的监控配置文件（如 Prometheus 的 scrape config、Zabbix 的 item 模板等），Agent 能自动识别运行环境并开启对应的数据采集。
- **价值**：大幅降低部署门槛，尤其适合微服务、容器化等动态环境。

### 2. **17年沉淀的大数据采集能力**
- 指 Bonree 自 2008 年起在 APM（应用性能监控）、IT 运维、用户体验监测等领域积累的采集经验。
- 包括对各种协议（HTTP/gRPC/JDBC/Redis/Kafka 等）、框架（Spring/Dubbo/MyBatis/FastAPI 等）、中间件（Nginx/Tomcat/Kafka/Elasticsearch 等）的深度适配逻辑。

### 3. **纳管自身和第三方探针，平滑升级**
- **自身探针**：指 Bonree Agent 本身可被平台集中管理（启停、版本升级、策略下发）。
- **第三方探针**：支持接入如 Prometheus Exporter、OpenTelemetry Collector、Zabbix Agent 等已有探针的数据，避免推倒重来。
- **平滑升级**：通过热更新、灰度发布机制，确保升级过程不中断业务监控。

### 4. **智能感知容器内部应用 & 主机进程**
- 在 Kubernetes 或 Docker 环境中，Agent 能：
  - 自动发现 Pod 中运行的应用类型（如 Java、Node.js、Go）
  - 注入对应语言的字节码探针（如 Java Agent）
  - 采集容器指标（CPU/Memory/Network）、日志、追踪数据
- 在物理机/虚拟机上，能扫描进程列表，识别 Web 服务、数据库、消息队列等，并自动启用相应监控模块。

### 5. **500+ 技术框架原生支持**
- 覆盖主流开发框架、中间件、数据库、云服务等，例如：
  - **Java**：Spring Boot, Dubbo, MyBatis, Kafka Client
  - **Python**：Django, Flask, FastAPI
  - **Go**：Gin, gRPC
  - **数据库**：MySQL, Oracle, MongoDB, Redis
  - **消息队列**：RabbitMQ, RocketMQ, Kafka
- “原生支持”意味着无需修改代码，只需加载 Agent 即可自动埋点（Auto-instrumentation）。

### 6. **支持 20万+ 探针数据上报**
- 表明其具备**超大规模集群的采集与传输能力**，适用于大型金融、电信、互联网企业。
- 通过数据压缩、批量上报、断点续传、本地缓存等机制保障高并发下的稳定性。

### 7. **自动发现、自动安装、自动监控**
- **自动发现**：通过服务注册中心（如 Nacos、Eureka）、K8s API、进程扫描等方式发现新服务。
- **自动安装**：通过 DaemonSet（K8s）、Ansible、SaltStack 或平台一键部署，实现无人值守安装。
- **自动监控**：识别应用类型后，自动启用对应的监控模板（如 Java 应用开启 JVM 监控 + Trace 采集）。

## 二、技术原理简析

### ▶ 架构设计
Bonree Agent 通常采用 **多模块插件化架构**：
- **Core Engine**：负责生命周期管理、配置同步、安全通信
- **Discovery Module**：服务/进程/容器发现
- **Collector Plugins**：按语言/框架/中间件分类的采集插件
- **Data Pipeline**：数据过滤、聚合、压缩、加密、上报
- **OTA Updater**：远程升级模块

### ▶ 自动感知原理
- **容器环境**：通过挂载 `/var/run/docker.sock` 或访问 K8s Downward API 获取 Pod 元数据，结合进程命令行参数判断应用类型。
- **主机环境**：扫描 `/proc` 目录或使用 `ps` 命令获取进程信息，匹配特征（如 `java -jar app.jar` → Java 应用）。
- **框架识别**：在 Java 中通过字节码增强（Bytecode Instrumentation）Hook 类加载器，检测是否加载了 Spring、Dubbo 等类。

### ▶ 无侵入采集原理（以 Java 为例）
- 利用 **Java Agent + ByteBuddy/ASM** 技术，在类加载时动态插入监控代码（如记录方法耗时、SQL 语句、HTTP 请求）。
- 不修改业务代码，仅需启动参数添加 `-javaagent:bonree-agent.jar`。

### ▶ 高可靠上报机制
- **本地缓存**：网络中断时暂存数据到磁盘
- **流量控制**：根据带宽动态调整上报频率
- **数据去重/压缩**：减少带宽占用
- **TLS 加密**：保障数据安全

# 附5: 拓扑智能构建技术
“**SmartTopo：实体关联拓扑智能构建技术**”是 Bonree ONE 可观测性平台中的一项核心能力，旨在**自动、实时、无侵入地构建 IT 系统的全局依赖拓扑图**。下面从**功能特性解释**和**技术原理分析**两个层面进行深入解析。

## 一、功能特性解释

### ✅ 核心目标  
**无需人工配置，自动发现并可视化 IT 系统中各类实体（如服务、主机、容器、数据库、中间件、API 等）之间的调用与依赖关系**，形成一张动态更新的“数字孪生”架构图。

### ✅ 关键特性说明

| 特性 | 说明 |
|------|------|
| **1. 无需人工配置** | 不需要运维人员手动绘制拓扑图或维护服务依赖清单（如 CMDB），降低管理成本，避免配置错误或滞后。 |
| **2. 自动从观测数据构建** | 基于真实运行时数据（如分布式追踪 Trace、日志、指标、网络流）推断出实体间的调用关系。 |
| **3. 实体类型全覆盖** | 支持识别并关联：前端页面、浏览器、移动 App、API、微服务、Pod、容器、虚拟机、物理机、数据库、缓存、消息队列、防火墙、负载均衡等。 |

| **5. 动态展示依赖关系** | 不仅展示“谁调用了谁”，还能显示调用量、成功率、延迟、错误率等性能指标，实现“拓扑即监控”。 |

> 🌰 举例：

## 二、技术原理分析

SmartTopo 的实现依赖于 **多源数据融合 + 智能关联算法 + 动态图计算**，其核心技术栈如下：

### 1. **数据来源：多维度观测数据融合**
SmartTopo 并非依赖单一数据源，而是融合以下四类可观测性信号（Telemetry）：

| 数据类型 | 作用 |
|--------|------|
| **分布式追踪（Tracing）** | 提供最精确的调用链路（如 OpenTelemetry Trace），明确 A → B → C 的调用顺序和上下文。 |
| **指标（Metrics）** | 如服务间网络流量、API 调用频次，用于辅助验证依赖强度。 |
| **日志（Logs）** | 通过日志中的 IP、服务名、TraceID 等字段，补充调用关系证据。 |
| **基础设施元数据** | 来自 K8s API、云厂商 API、CMDB 的主机/IP/容器标签信息，用于实体识别与命名。 |

> 🔍 例如：即使某个旧系统未埋点 Trace，但其 Nginx 日志中记录了上游服务 IP，结合网络流量突增，也可推断出潜在调用关系。

---

### 2. **实体识别与标准化（Entity Resolution）**
- 对来自不同系统的原始数据（如 Pod 名、IP、服务名、URL）进行**归一化处理**，映射到统一的“逻辑实体”。
- 使用规则引擎 + 机器学习模型识别：
  - “`10.244.1.5:8080`” 属于 `user-service` 的 v2 版本
  - “`jdbc:mysql://db-prod:3306/order`” 对应 `MySQL-order-db`

---

### 3. **依赖关系推理（Dependency Inference）**
- **基于 Trace 的强依赖**：若 Trace 中存在 Span A → Span B，则建立 A → B 的调用边。
- **基于流量的弱依赖**：若服务 X 持续向 Y 发送大量 TCP/HTTP 流量，且无 Trace，则标记为“疑似依赖”，供人工确认或后续验证。
- **时间窗口聚合**：在滑动时间窗口（如 1 分钟）内统计调用频次，过滤瞬时噪声。

---

### 4. **动态图构建与存储**
- 将实体作为**节点（Node）**，依赖关系作为**边（Edge）**，构建属性图（Property Graph）。
- 使用图数据库（如 Neo4j、JanusGraph）或自研图引擎存储，支持高效查询：
  - “哪些服务依赖数据库 DB1？”
  - “如果 payment-service 宕机，会影响哪些业务？”
- 拓扑图按业务域、环境（dev/staging/prod）、版本等维度分层展示。

---

### 5. **实时更新机制**
- Agent 或 Collector 持续上报新数据 → 流处理引擎（如 Flink/Kafka Streams）实时处理 → 更新图数据库。
- 前端通过 WebSocket 或 SSE（Server-Sent Events）接收拓扑变更事件，实现**秒级刷新**。
